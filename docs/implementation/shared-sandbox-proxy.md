# Shared sandbox proxy channel — Issue #101

Implemented on 2026-10-26 for the behaviour-test infrastructure. This changes only `tests/behaviour/` and documentation; the Release Version stays 2.1.0 under MCP/SQLite §14.3. No product rule, MCP tool, everyday launcher or real service changes.

## One route implementation

`tests/behaviour/proxy.ts` contains the selector and validator originally delivered by PR #99. Runner, host and reviewer import it directly; the temporary compatibility exports were removed during independent review. There is no second parser or proxy-rule generator.

The Batch CLI and interactive host select exactly `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `http_proxy`, `https_proxy`, and `no_proxy`. Codex selects only terminal values and never opens Claude settings. Claude additionally uses the corresponding `env` key in `~/.claude/settings.json`; a terminal value, including an empty string, wins. B03b reviewers deliberately keep #99’s approved policy for both CLIs: terminal values take precedence over the six settings env keys. This is separate from the tested client’s source policy. No other settings fields or environment entries are forwarded. For Claude, missing settings are allowed; invalid JSON, invalid shape, unreadable settings or non-string selected values stop setup with fixed diagnostics that contain no paths or values. Tested Codex clients are unaffected by missing or malformed Claude settings; both B03b reviewers refuse malformed settings. The client cannot read the source settings file. Invalid runner CLI proxy configuration produces one `refused:` line before any subscription read, not a stack trace.

`writeProfile(..., { proxyEnv })` validates the selected values, creates the TCP exceptions and returns the normalized `profile.proxyEnvironment`. All consumers must launch with that returned environment, so native routing matches the installed policy. The MCP-only runner, Dedicated Entry driver and both interactive clients do this. The latest main brought in the B02d Dedicated Entry driver; its real-launcher/fake-client Batch now forwards the same normalized proxy environment on both turns. This is model-free integration evidence, not a completed real-model onboarding run.

Only HTTP(S) proxy URLs whose parsed hostname is `localhost` or `127.0.0.1` are accepted. They normalize to `127.0.0.1`; each grants only IPv4 TCP on its parsed port (default 80/443). Ports 18765/18766 are refused before launch, even on an otherwise unsupported hostname. IPv6, mapped IPv4 and other proxy hosts are refused. Empty proxies and bypass lists add no exceptions. The validator also refuses any registered harness service/relay port and the caller's `localPorts`/additional `protectedPorts`. `startService` and `startRoute` register their ports (including a relay's upstream) until shutdown. Proxy grants stay reserved while their runner-owned control directory exists; later harness endpoint allocation excludes those grants. Runner and host also exclude configured proxy ports before allocating their own listeners, so a down proxy cannot have its port reused as a service/relay. This ownership registry is process-local. The shared API accepts additional `protectedPorts`, but the Batch CLI and interactive host expose no cross-process inventory option; their operators cannot supply that inventory through a command flag. For approved runs, do not configure a proxy port inside the host’s ephemeral allocation range: query `sysctl net.inet.ip.portrange.first net.inet.ip.portrange.last` and use a stable proxy listener outside it. A down proxy in that range can otherwise be replaced by another controller’s dynamically allocated relay. This restriction is operational, not automatically enforced; the owned ephemeral fake proxies in isolated tests are not a recommendation for real routing.

Automatic MCP-only and Dedicated Attempts, and [interactive sessions (#118)](interactive-proxy-forwarder.md), put an owned TCP forwarder between the client and each configured proxy endpoint. Only the forwarder ports appear in the client environment/profile, and opaque in-memory permits allow only their creating controller to grant those protected ports. The original proxy ports stay denied. Automatic forwarding is enabled while clients in the current sequential/concurrent turn group are running; the last client exit immediately disconnects existing sockets and disables new forwarding. Its initial idle, inter-group idle and final observation windows each last 500 ms. Interactive forwarding follows the wrapper’s acknowledged start/exit signals; it stays inactive before/after that session and has a final 500 ms observation. Any connection while inactive is counted as residual-process evidence and makes the Attempt `driver-failed`; final observation is followed by closure. `raw/proxy-channel.json` and the automatic `proxy-channel` Controller event (interactive: `isolation.json.proxyChannel`) retain counts and closure status, never endpoints or credentials. Forwarding ports and every relay/service/bait port granted in a client profile are retired from later harness allocation in that controller process, even after their listeners and control directories close. Retirement records numbers in this controller, not an OS-wide reservation.

The client retains its own relay (Dedicated Entry’s authenticated isolated service) and the existing scenario-specific bait exception where required. Every other local TCP endpoint remains denied. All IPv6 TCP/UDP and local IPv4 UDP are denied, including mapped-zero and UDP on an allowed TCP port. When an Attempt/session forwarder is enabled, all other outbound traffic, including public IPv4 TCP/UDP and Unix-domain socket connections, is denied. A client that ignores proxy variables fails closed in that mode. No-proxy clients and #99 reviewers keep their previous public IPv4 policy. The initially added blanket IPv4 UDP deny was removed during review: it was unnecessary for local isolation and changed reviewer/public-network behaviour. The IPv6 UDP deny remains necessary because Seatbelt's localhost matcher misses mapped-zero destinations. The permitted proxy is trusted: Seatbelt checks the socket destination, not a subsequent HTTP CONNECT target, so it cannot prevent a trusted proxy from forwarding to another local service. No stronger transitive-destination guarantee is asserted.

## When to enable and how to record a Batch

Controller, historical-author, ChatGPT observer and both runners’ session-relay HTTP requests use private `node:http` agents with explicit `proxyEnv: {}`, passed at every authenticated request site. The Controller SDK receives a fetch adapter pinned to its owned loopback MCP endpoint; it uses that agent for POST, GET/SSE and DELETE, preserves cancellation and never follows redirects with a credential. Agents are destroyed when their owning connection closes. Node's global fetch/agent and proxy settings from argv, NODE_OPTIONS, environment or explicit/default JSON configuration files therefore cannot route these credentials through a proxy. The previous source-text refusal has been removed: correctness is in the transport, not in identifying every way to enable Node proxy mode. No ambient environment/global agent is changed, and the tested client's selected six proxy variables still use its own Attempt channel.

A non-empty selected HTTP(S) proxy variable opens its narrow channel automatically at setup; no extra switch or separate firewall policy is needed. Use it when that approved client's network route requires a local HTTP proxy. This is routing setup, not authorization to spend model quota: the existing Batch gate still applies.

For a Codex run, absent or empty HTTP(S) terminal proxy variables leave the channel closed; Claude settings have no effect. For a Claude direct run, explicitly empty the four HTTP(S) terminal variables if settings would otherwise supply them. `ALL_PROXY`/`all_proxy` are never forwarded. Bypass values are preserved, not silently amended; when using a proxy, confirm that the intended relay bypass is present in `NO_PROXY`/`no_proxy` and verify actual MCP reachability in the approved probe. In the first supervised automatic proxy-mode Codex probe, also check whether the client needs Unix-domain socket connections; they are denied in this mode and must not be silently re-enabled. Invalid Claude settings still stop Claude setup rather than fall back to direct access.

The approved Batch description distinguishes the tested client from B03b reviewers and records the client/version, whether the channel is enabled, selected variable names and their source (terminal/settings), intended direct/proxy route, and the native-client IPv4/proxy probe result. Keep URL values, userinfo, bypass-list values and credentials out of the description and repository. Runtime records add only `{ enabled, variables }`: `batch.json` and per-turn isolation events for the runner, `isolation.json` for the interactive host. The protected launcher manifest necessarily carries the selected environment and remains private. `proxySecrets` supplies runner/host redaction with original and normalized proxy URLs plus non-empty userinfo, username and password, in their original, decoded and percent-encoded forms. Basic proxy authorization and lowercase percent escapes are included. JSON/JSONL validation is followed by string-token edits: known full secrets and proxy components of at least eight characters are scrubbed in keys and every string value, including unknown fields. Unchanged tokens, whitespace, escapes, number spelling/precision and booleans survive byte-for-byte. A rewritten key collision or change to a protocol discriminant causes a fixed refusal. Short proxy components are recognized only in credential fields, labelled text and standalone echoes; ordinary keys and common words such as `run` or `id` are preserved. An independent scan checks the full text and decoded JSON string tokens for complete/opaque secrets; only short components use contextual checks. Raw files and copied artifacts must pass that check before retention: a failed raw file is withheld, named in `missing`, and makes the Attempt `driver-failed`. The saved Attempt also passes required-field, schema, completeness and leak checks before publication. Arbitrary encodings, ambiguous short words and unidentified login output are not exhaustively covered; raw evidence stays private.

Known proxy components of at least eight characters are scrubbed everywhere. A long common username such as `developer` or `response` can therefore collide with protocol role/type values and withhold a record after a client has run. Record this fail-closed limitation when approving a Batch; there is no new credential-changing or real-credential preflight probe in this PR.

Do not rerun an earlier approved Batch against this change silently. Confirm that its client, route, Scenario and ceiling still match the approval, preserve the failed prior Attempt, and use a fresh Attempt directory. Any real availability check remains with the coordinator under that approval.

## Does Codex need the proxy?

**Codex supports an explicit proxy, but a requirement to use the known daily local proxy was not established.** The original investigation’s shell snapshot had no proxy variables, and a passive snapshot of existing Codex TCP connections found non-loopback connections and no connection to the known daily proxy. Consequently, do not mark every Codex Batch as requiring that proxy. The reviewed implementation therefore selects tested Codex clients’ proxies only from their terminal, matching the everyday Codex and Dedicated Entry launcher. This corrects the first PR revision, which also consulted Claude settings for Codex.

Evidence collected without a model call or a real proxy connection:

- Installed npm package: `@openai/codex` 0.164.0. Static executable inspection found the eight conventional proxy variable names and reqwest 0.12.28 paths; only presence was printed.
- This worker terminal: the six supported names plus `ALL_PROXY` and `all_proxy` were all absent. In Claude settings, only membership of those names in `env` was inspected: the six supported names were present, the two ALL names absent. No configuration value, credential field or login file was inspected for this inventory.
- Passive `lsof` classification of existing Codex sockets: loopback and non-loopback established connections existed; the known daily proxy was not observed. This does not attribute every socket to a model request, prove every other terminal's environment, or exclude VPN/TUN/network routing below the application.
- System proxy observation reported only flags: HTTP/HTTPS/SOCKS disabled, automatic proxy configuration enabled. No PAC URL/content was read or fetched. These flags do not prove which route any individual request chose.
- `node tests/behaviour/runner/codex-proxy-probe.ts` ran the installed binary's **`mcp login fixture`**, with an empty HOME/CODEX_HOME, an invented `.invalid` MCP endpoint, a fake proxy that always returns HTTP 502, and Seatbelt allowing outbound traffic **only** to that owned proxy. It neither authenticates nor invokes a model. The expected nonzero exit is the deliberately failed fake discovery, not evidence of real login/API availability.
