# Answer Desk viewer (#113)

This slice implements [Answer Desk §5, §7 and §9](../spec/answer-desk.md) on the existing Map viewer. It ships as Release Version 3.4.0 **disabled by default**, using the same `answerDeskEnabled` setting introduced by the storage slice. It changes no MCP tool or workflow text. Delivery transport and coordinated real-client/ChatGPT acceptance remain separate work.

## Browser boundary

`POST /api/desk` is the only browser write route. Its JSON body contains `mapId` and one of:

- `action: "answer", submissions: [{questionId, questionVersion, choice: {option} | {text}}]` for a single answer or replacement. Multiple submissions are admitted only for pending `followRecommendation` questions and their displayed recommended option; storage commits them atomically.
- `action: "reopen", submission: {ticketId, settlementIntroducedAtRevision, affectedTickets, affectedSettlementRevisions, requested}` to file or replace a Reopen Request.
- `action: "cancelReopen", requestId` to cancel a pending request.

The host first enforces the exact loopback Host. The route requires exact same-origin `Origin`, rejects foreign `Sec-Fetch-Site`, accepts JSON up to 1 MiB and checks `X-Wayfinder-Key` against a constant-time SHA-256 comparison. It accepts no query, MCP credential, Map command, taking operation or Settlement. It returns fixed errors and no diagnostic text. Responses retain no-store, no-referrer, same-origin resource policy and the viewer CSP. The ChatGPT relay remains unchanged and forwards only `/mcp`.

With the setting absent or false, `/api/desk` returns 404 for every method, `/viewer/desk.js` is unavailable, view responses omit `desk`, the page has no Answer Desk UI (including an already-open page after a disabled restart at the same Revision), and revision polling still returns 204 when unchanged. Every other viewer route remains GET/HEAD. With the setting on, reads remain unkeyed; keyless pages can inspect desk state but have no enabled response controls.

## Key issuance and handoff

`createViewerKey` generates 32 independent random bytes per enabled service process. Nothing derives it from the MCP token or stores it in a Map. `LocalServiceConfiguration.answerDeskKeyPath`, exposed as the operator-only `WAYFINDER_ANSWER_DESK_KEY_FILE`, optionally publishes it after listener startup. The file's parent must already be a current-user private directory; the destination must be absent or a private regular file. Publication uses an exclusive temporary 0600 file and atomic rename, refusing symlinks. Startup failures print only existing fixed operator errors. Normal stop removes the matching file, and every restart creates a different key even after a crash.

The launcher sets that file path to `answer-desk-key` in its private service directory. `wayfinder desk <mapId>` verifies its ownership/type/mode, checks the enabled read projection, then opens `http://127.0.0.1:<port>/maps/<mapId>#key=…` in the macOS default browser. It sends `open location` over a pipe to the fixed `/usr/bin/osascript -` executable, which dispatches an Apple event. The key is in stdin only, never argv or environment; the child receives only a fixed `PATH`, both diagnostic streams are discarded, and the launch times out after 30 seconds. `BROWSER` is deliberately ignored. Unsupported platforms fail before starting a service or reading its key, with a fixed message explaining that the secure browser entry currently supports only macOS; there is no generic-browser fallback. This retains the specified fragment handoff without adding another HTTP capability or bootstrap endpoint.

The command neither enables the feature nor prints the URL or adds a launch-metadata record. The launcher regression uses a real executable that records its argv/environment as `BROWSER`: an unkeyed probe proves the recorder works, then the desk launch must leave its keyless output untouched. A second real subprocess stands in for the OS Apple-event endpoint, verifies the exact production argv/environment and captures the URL only from stdin. It attempts to echo that stdin to stdout/stderr on both success and failure; neither stream reaches the launcher output. No real browser, harness or service is opened by this test.

The fragment remains in the URL until the first successful read projection confirms the desk is enabled (including while that read is delayed or failing). Once confirmed, the viewer reads the fragment, immediately strips it with `history.replaceState(null, …)` and retains the key only in closures. A disabled viewer neither reads nor removes the fragment. The enabled key is not in DOM attributes, history state, cookies, browser storage, global variables, returned data, scripts or service logs. Refreshing or opening another page requires the launcher again. A service restart rejects an existing page's old key; the UI reports that it must be reopened. Same-user private-file access is an operator capability, not an MCP privilege: an unrestricted same-user process can still read the private key file. Fragment stripping does not promise erasure from the browser's own history database; restart invalidates any retained old key.

## Projection and interaction

When enabled, the existing `/api/maps/<mapId>/view?known=<revision>` returns a fresh coherent head/desk projection every two seconds, even when the Revision is unchanged. The page avoids repainting unchanged desk content, and preserves a text modal and draft across both desk changes and new Map Revisions. It retains the viewer's unreachable/stale indication. Human writes call the existing guarded storage seam and never advance a Map Revision.

The queue uses the service's order without recomputing it: unlock/research gates, Unlock Count, Downstream Count, triage, time and identity. Each question shows consequences, why Kun is needed, triage reason, full recommendation and two or three options. Option clicks submit immediately. Global Enter submits the displayed question's explicitly labelled recommendation, 1–3 select its options and `t` opens its text draft, only while that exact question ID and Question Version is armed. A focused queue, history or option button cannot redirect these shortcuts. Tab navigates controls and Space activates buttons; text inputs and open dialogs retain their native keys. Empty text, viewing, opening and cancelling submit nothing. Bulk confirmation shows every selected full recommended answer in a modal; it captures the displayed Question Versions and does not silently rebind them after a poll.

Clicking the current question or selecting a named queue/history question arms it immediately. Successful answers advance to the first pending question in service order; this own-action transition, closing a dialog, and filing/cancelling a Reopen Request arm the displayed question after `SHORTCUT_ARM_DELAY_MS` (600 ms). A highlighted card and visible message mark the waiting period; another Enter inside it cannot answer the next question. Unrelated publications, delivery updates, queue reordering and Map Revisions preserve both an armed identity and a running delay. Focus falling to BODY or the page root does not change either the current question or its shortcut authority. The first question on page load remains paused.

A changed question ID/Question Version or loss of its live state (withdrawal, replacement, Settlement or reopening) cancels any timer and keeps the old reading context with “问题已变，请重新选择题目后再回答。” That pause persists across subsequent polls, including an empty queue followed by new questions, and cannot be cleared by closing a dialog or completing an outstanding write. A different default becoming current without Kun's action is also unarmed. Kun explicitly selects a queue question or editable answer to restore shortcuts. “已了解，查看当前题目” releases the old-context interruption, including with no live questions, but does not arm a default card. A window blur suspends shortcuts; refocus refreshes first to catch changes while polling was suspended, then waits 600 ms only if no external change required reselection. Failed refreshes never authorize a new shortcut.

Answered and Taken answers remain editable until Settlement. Withdrawal strikes through the question and displays its reason. Old answers and superseded publications appear as history. Requested-option markers remain visually separate from submitted answers and recommendations; text Reopen context is displayed verbatim with no prefilled answer. The browser test checks that a marker for option 2 still makes Enter submit recommendation 1.

Every settled Ticket, including a conversation-only Settlement, offers a Reopen Request. The modal captures the target and dependent Settlement identities and displays the full affected list before filing. The storage transaction verifies the entire binding set. If it changes, filing is refused and the modal requires explicit review of the new list; nothing is filed or replaced. Conversation-only Settlements offer text only. Pending requests can be cancelled; Taken requests can only be replaced after another review. The page never reopens or settles a Ticket itself, retries an unknown receipt or treats a Quiet Window as automatic Settlement.
