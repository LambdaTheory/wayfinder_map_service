# Capturing a real problem

Maintainer entry point for [R6](../spec/behaviour-testing.md#r6-real-problems-become-scenarios), Issue #71 (B04). A report and an analysis finding use the same path. The capture command reads one SQLite Map at a named Revision and writes a seed, a Scenario skeleton and an audit record. It starts no service or model, retrieves no conversations, and modifies neither the source database nor the Scenario library.

## Prepare the evidence

1. Locate the source session and the Revision **before** the incident. Record a portable session/turn reference and the human's exact words. Retrieving words automatically belongs to B08. Keep raw records, database paths and the input manifest outside the repository.
2. State the Scenario's purpose and the accepted correct behaviour, with its rule or human-ruling reference. Write both forbidden outcomes and at least one positive expectation. If words are missing, set `humanWords` to `null`; if correct behaviour is unresolved, set `verdict` to `null`. Do not fill either gap with a plausible reconstruction.
3. Choose `current-visible-state` or `history`. For **each current Claim**, explicitly choose `keep` or `clear` and explain how it follows from the purpose. No default clears Claims. A test of takeover keeps the other session's Claim; a test of a particular question while advancing a Ticket may clear only that incident-session Claim and restore the working context in the opening.
4. Record the original harness/model, Entry and effort (state unknowns explicitly). Keep the verbatim `humanWords` separate from `replayContext`, such as a Map-resume preamble. List private literals to redact. Follow B01: replace local evidence paths with `<private-evidence>/<file name>`; preserve a distinguishing suffix such as `evidence/` when the accepted fixture already uses it. Redact credentials and unrelated personal data explicitly too.

Start from [`capture/example.json`](../../tests/behaviour/capture/example.json). Its words, IDs, claims and verdicts are synthetic examples, not defaults for a real incident. The typed input contract is [`CaptureInput`](../../tests/behaviour/capture/capture.ts). `redactions` contains exact literal values and public replacement strings; it is private input and is never copied to output. The output records each replacement's rule ID, JSON-pointer location and occurrence count without the original value. A replacement cannot contain any declared private literal, and the entire output is checked for declared literals, including the redaction record and the fully joined opening turn. Every string is checked directly, without JSON escaping, for both declared literals and common residual private paths and bearer credentials; it is not a complete secret detector. Review all three output files before admission.

## Run capture and inspect the output

Use Node 26.3.0 and build this checkout first. Capture and its synthetic fixture builder use the same built domain implementation as the runner, loaded only when conversion starts; importing the capture module does not require a build. Supply the three paths as quoted arguments; do not put the source path into a public transcript.

```sh
npm run build
node tests/behaviour/capture/cli.ts "$SOURCE_DATABASE" "$CAPTURE_INPUT" "$FRESH_OUTPUT"
```

`FRESH_OUTPUT` must not exist and its parent must exist. The command reserves a private directory and never replaces existing files. If interrupted during output, treat the directory as incomplete and retry with a fresh destination. It prints only the Scenario ID and intake statuses. Expected errors describe the missing requirement; filesystem/SQLite/JSON errors have a generic message so private inputs do not leak to a shared log. The exported `captureProblem(database, input)` API supports private local diagnostics.

| File | Review |
| --- | --- |
| `seed.json` | B01 `Seed`: restoration mode, Map data, `derivedFrom` and conversion record |
| `scenario.json` | Harness-neutral B01 skeleton with the actual turn, must-not items, positive expectations and `pending` reasons |
| `capture.json` | Source/words, Claim decisions, redaction locations, seed SHA-256, verified source Revisions, verdict status and all reproduction Attempts |

Before SQLite opens anything, capture reads the file header and checks for `-wal`, `-shm` and `-journal`. A WAL-mode file or any sidecar is refused: even a read-only SQLite connection can create sidecars. The accepted input is a quiescent, consistent private database copy in `DELETE` journal mode without sidecars; do not let another process write or switch its journal mode during capture. The connection then uses SQLite `mode=ro` and `readOnly: true`, in one read transaction, without initialization, migration or checkpointing.

Obtain that private copy through the service's [consistent backup command](../spec/mcp-sqlite.md#10-manual-consistent-backup), `npm run --silent backup -- "$SOURCE_DATABASE" "$PRIVATE_COPY"`, in a private directory such as `~/Library/Caches/wayfinder-behaviour-tests/`. A running database's main file alone is not a complete backup. Any recovery, checkpoint or `PRAGMA journal_mode=DELETE` conversion must operate **only on that private copy**, never on the source or the everyday service; capture itself refuses such inputs rather than operating the source. Do not use `immutable=1` to bypass this check: it can ignore committed WAL data. Missing files, incompatible format, missing Map/Revision, gaps and inconsistent Revision envelopes also fail. Tests cover a cleanly closed WAL database with no writer and unchanged source-directory entries, plus active WAL and sidecar refusals.

## State and history boundaries

`current-visible-state` restores Map text, Tickets, Dependencies, content, Settlements and chosen Claims. It does not restore source Revision numbers, Settlement introduction Revisions or original authors. The tool replays the generated seed through the domain commands in memory and compares the resulting visible state with the converted source. B01 omits empty Map/Ticket/Settlement extension containers; a nonempty container is refused rather than silently lost. Evidence extensions are preserved.

`history` reads Revisions 1 through the selected Revision. SeedMap's title, Destination and Notes are **creation inputs**; its Tickets, Fog and Scope Exclusions describe the expected head. Each later source Revision becomes one `map_apply`, with its source client ID as the historical author label. The tool validates **every complete Revision state**, including Revision numbers, Claims and Settlement introduction Revisions. Creation is attributed to the Controller; the audit record retains the source authors, timestamps and semantic summaries. Replayed timestamps and actor IDs are new, and reconstructed command arguments are not claimed to be the original tool calls.

SQLite stores Revision states and semantic summaries, not full command arguments. An acquire-and-release within one Revision can hide the Claimant at both boundaries; an acquire(A), release(A), acquire(B) sequence also hides A even though B remains visible. When a transient Claimant or another argument needed to reproduce the stored state cannot be determined, capture fails and requires a `historyOverrides` entry with the Revision, original `commands`, a reason and a portable evidence reference. Supply it from actual evidence; do not guess. Overrides must still reproduce the exact Revision state. Intermediate text overwritten within one Revision (for example, two `map.update` commands or `ticket.create` followed by `ticket.update`) is reconstructed from the final stored state; this does not recover the original intermediate wording. Use an evidenced override when that wording matters to the Scenario. Redaction that collapses two distinct Revision states, unsupported initial extensions, or a creation-only history cannot be silently repaired; use a justified different seed mode or settle the format limitation separately.

A requested current Claim clearance in history mode adds one final **Controller** Revision; it never deletes that Claim from the historical Revision states. The runner registers separate temporary credentials for historical author labels, replays each step, checks the expected Map text, Tickets and content, and records the seed-head boundary after every successful write. A lost reply triggers a head reread while the setup failure is retained; if that read also fails, the final catalog export supplies the boundary because no agent turn has started. Seeding, including a partially failed restore, cannot count as agent success. Historical credentials are never given to the agent and are included in normal token redaction. The runner requires an original client ID that does not collide with its newly allocated Controller or agent identities; a collision is rejected before service launch (the Attempt currently records this prelaunch setup error as `service-failed`). Capture also rejects a historical client literally named `controller`, which the unchanged B01 format reserves as a Controller role marker; it never silently substitutes an identity.

## Reproduce, retain and admit

1. Review the skeleton and wire available script checks in `scenarios/`; generated criteria default to model review and are not evidence that a behaviour happened. Add any required-event checks and fixtures for a Conflict, restart or other trigger. Check the source words and purpose before removing `pending`.
2. Have the coordinator request approval for two Attempts on the original Combination. Capture never runs those Attempts. Keep every result with Batch/Attempt IDs, Entry, effort and a portable evidence reference. Re-run capture into a fresh output directory with `reproductions` filled, retaining earlier artifacts.
3. If the wording alone does not reproduce, record added context or a full-environment comparison in that Attempt's `changedConditions`. Record changes of Entry, effort and isolation too. Incomplete runs are not non-reproductions; duplicate Attempt IDs are rejected. Two unchanged non-reproductions on the original Combination, Entry and effort produce `not-reproduced-twice`, never “fixed” or “pass”. If the original Entry or effort is unknown, the result remains `pending` with that reason in both the capture record and Scenario references; no unchanged baseline comparison is invented. A reproduction on the original harness/model can be retained with its changed conditions visible.
4. Admit the reviewed seed, Scenario and redacted capture record together: put the Map in `seeds/`, the record under `captures/<id>/`, and the Scenario in `scenarios/`; register its stable ID in both `library` and `candidateIds` in `library.ts`. Use `seed.derivedFrom` for the conversion and `source.refs` for the capture record and result summary. **Two non-reproductions do not remove the Scenario or block admission.** The generated Scenario also carries the reproduction status in `source.refs`. Keep that mark beside the source and keep all Attempts. Future verdict changes increment Scenario version per R5.
5. A missing-word or unresolved-verdict capture stays as a **paused intake draft** under `captures/<id>/`, including the incomplete skeleton and its explicit structural errors. B01 requires a real turn and positive expectations for an executable Scenario; the tool does not fabricate either to make validation green. Both `cli.ts list` and `cli.ts validate` discover `captures/*/capture.json`, list each intake status and count paused drafts separately from executable Scenarios. Link the draft from the tracking Issue, then complete it when the evidence or human ruling arrives. It is not a runnable Scenario and must not be omitted from an intake report.
6. Run `node tests/behaviour/cli.ts validate`, then `npm test` and `npm run typecheck`. Link the result summary and source record in the Issue/PR. The original words, seed, verdict, reproduction status and library location should each be reachable from one source reference.

## F11 trace

The source is Map `DistributedAgents.Feishu.20261023`, Revision 10 before the incident at Revision 11, in interactive Codex with `gpt-6-astra` on 2026-10-23. B01's source reference is the acceptance review of 2026-10-24 §3.4 (“incident 9”); its public fixture does not include the native session ID. The exact question is **「这部分权限，似乎是Agent，而不是飞书的？」**. The replay adds a separately identified Map/D03-resume preamble.

[`seeds/f11.json`](../../tests/behaviour/seeds/f11.json) remains unchanged. [`F11.seed.derivedFrom`](../../tests/behaviour/scenarios/safety.ts) preserves the original conversion: visible state only, one D03 Claim cleared for a new-session replay, 25 private path occurrences redacted, Notes and question retained. [`captures/f11.json`](../../tests/behaviour/captures/f11.json) connects those records to the exact must-not and expectation IDs, the admitted library entry, all three reproduction Attempts, their limitations and [product Issue #87](https://github.com/kun-g/wayfinder_map_service/issues/87).

The [B1 and B2 summaries](behaviour-runs.md) supply the already approved reproduction evidence: Codex · gpt-6-astra · xhigh, MCP-only, release 2.0.2, three Attempts violating `rewrote-map` and `scope-changed-on-question`. B1 had isolation gaps; B2 repeated under the allowlist sandbox. The positive model-reviewed item remains open in those summaries. These are reproductions of the scope-change problem, not a claim that every detail of the original incident recurred. [Issue #71's evidence comment](https://github.com/kun-g/wayfinder_map_service/issues/71#issuecomment-6399430980) links the first two Attempts; no new model Batch is required by B04.

The public-fixture consistency check is in [`capture/capture.test.ts`](../../tests/behaviour/capture/capture.test.ts): a temporary synthetic SQLite database is reconstituted from the public F11 seed, its documented Claim and synthetic private path prefixes. The new command's conversion produces a deeply equal SeedMap and exactly 25 location-specific replacements. It does not establish whether the original private redaction was complete, reopen the private source or assert that a second source capture occurred. Private-source verification remains with the coordinator after integration, as required by the dispatched work boundary. A separate **new synthetic** 28-Revision fixture exercises restoration, reopening, Claims, Settlements, Dependencies, content and author labels in memory and through a disposable service. The historical prototype's “28 Revisions restored identically” is background validation material, not evidence for this implementation.

## Implementation verification

The initial implementation and subsequent review rounds were verified on Node 26.3.0 with `npm run build`, `npm test`, `npm run typecheck` and `node tests/behaviour/cli.ts validate`. Fixed-data tests cover source immutability, selected Revisions, current/history seeds, per-Claim choices, final-output redaction, missing data, ambiguous history, retained non-reproductions, paused verdicts, F11 fixture consistency and historical seeding attribution. The [review follow-up](behaviour-capture-review.md) records the current validation totals and regression evidence. No model Batch was run.

Standards self-review checked the read-only storage boundary, source/output privacy, refusal of lossy history and preservation of partial seed boundaries. Spec self-review checked R1/R3/R6, F11's published B1/B2 evidence and the unchanged B01 format. It found and fixed normalization of optional content References in history-head verification. Only tests and documentation change; the shipped Release Version remains unchanged. Independent review and merge belong to the coordinator.

The subsequent [two-review follow-up](behaviour-capture-review.md) records required corrections, red-to-green regressions and validation results for each round. In particular, the earlier source-byte checks did not cover creation of WAL sidecars, and the earlier partial-seeding check did not cover a lost commit reply; both now have explicit regression cases.
