# Behaviour Scenarios

The Scenario library and evidence contract of the [behaviour testing requirements](../../docs/spec/behaviour-testing.md) (B01, Issue #64). Scenarios describe how an agent in a real client must behave on a Wayfinder Map; Drivers (B02 onwards) start clients against an isolated service and record what happened; verdicts (B03) judge the record.

Library inspection starts no service or model. Automated tests use disposable services with fake clients; manual runners start isolated services, and runs that spend model quota happen only inside a Batch Kun has approved. Raw conversations and run records stay in a private directory outside the repository.

## A Scenario

- **Identity and source:** a stable ID, a `version` raised whenever a verdict item changes, and a source: real problem or design hazard, what happened, portable references (Map ID and Revision, date, Issue). Diagnostic probes are not Scenarios.
- **Applicability:** the Entries (`mcp-only`, `dedicated`, `chatgpt`, `matt`) and client capabilities it needs. A cell stays "not onboarded" until that client's Driver passes the five onboarding checks of R2.
- **Seed:** Maps rebuilt to their current visible state, or (`restores: 'history'`) replayed Revision by Revision with their original authors when the Scenario depends on history; plus fixtures. A seed taken from a real Map lists every conversion step, including Claims kept or cleared and redactions.
- **Turns:** each `reply` names the proposal it answers and a runtime cue; the runner sends it only after that proposal appeared, and the precondition is judged again afterwards. `nudge` turns carry no answer.
- **Controller actions:** conflicting writes, cut routes, restarts. Each action that should provoke a reaction needs a script-proven required event.
- **Verdict items:** `requiredEvents` are proven first; any confirmed `mustNot` fails; every `expect` group needs evidence for one of its equivalent ways. Items are judged by script, or by a model or the human with a written criterion. An item whose correct behaviour is not yet decided is `paused` and goes to the human.

Script checks answer `holds`, `violated` or `unknown`. Missing records (the `missing` markers of `evidence.ts`) or a write without a receipt never become `holds`; only a receipt places a write in a session and turn.

## Adding a Scenario

1. Write it in the matching file under `scenarios/` and add it to `library.ts`; a new real problem also gets its ID in `candidateIds`.
2. Write must-not items as the wrong action itself and expectations as the right action, each with the evidence that proves it.
3. Run `node tests/behaviour/cli.ts validate` and `npm test`.
4. A real problem starts from the Revision before the incident and the human's own words (R6). Follow the [capture maintainer guide](../../docs/implementation/behaviour-capture.md) to generate and review the seed, conversion/redaction record and Scenario skeleton. Two non-reproductions retain the Scenario; missing words or an unresolved verdict retain a paused intake draft without invented text.

## Running a Batch

```sh
npm run build    # the runner serves this checkout's dist/
node tests/behaviour/runner/run.ts --batch B1-20261025 --scenarios S0b,F11 --count 2 --ceiling 4 --model gpt-6-astra --effort xhigh
```

Run only a Batch Kun approved: it spends model quota. Every Attempt gets a new database in a fresh directory under `~/Library/Caches/wayfinder-behaviour-tests/`, a free port (never 18765 or 18766), a Controller credential and one credential per session, so MCP-only Revisions name the session's credential; Dedicated uses the launcher's real Client ID and separately records each launch credential. Records default to `~/Library/Application Support/Wayfinder/behaviour-runs/<batch>/<attempt>/`; the temporary database and credentials are removed after successful history export and service shutdown. For MCP-only, a failed history export removes the credential file and retains the database at `isolation.retainedDatabase`. Dedicated always removes its raw database, including after export failure, because persisted Map text can contain client credentials; it retains redacted `maps` JSON instead and marks `raw.database` missing. A failed Dedicated export additionally marks `maps` missing and the Attempt `driver-failed`. Cleanup outcomes are recorded individually. The Controller seeds the Maps with the current release's `version`; the agent must find its own `version` in what its client shows it.

Codex runs with a private `HOME` and `CODEX_HOME`, `--ignore-user-config` and only this run's Wayfinder server. Seatbelt denies file reads by default and grants only the session HOME, the fixture workdir, explicitly prepared content, exact Node/Codex installations and an explicit OS-runtime list. File writes are limited to its HOME, fixture directory and scoped device access: `/dev/null`, `/dev/tty`, `/dev/dtracehelper`, the standard descriptor aliases `/dev/stdin`, `/dev/stdout`, `/dev/stderr` and numeric `/dev/fd/N`, plus newly allocated ptys. Descriptor aliases duplicate only descriptors the client already holds. `pseudo-tty` and literal `/dev/ptmx` grants allow allocation; slave paths matching `/dev/ttys[0-9]+` require the per-sandbox `com.apple.sandbox.pty` extension. Its controlling terminal is readable through `/dev/tty`; ptys created outside this sandbox instance remain unreadable and unwritable by name. `file-ioctl` explicitly denies `TIOCSTI`, including on inherited stdin, so the client cannot queue commands for the unsandboxed operator shell. Window-size queries, terminal attributes and raw mode remain available. Other temporary directories, personal caches, service storage and runner controls remain unreadable without needing a list of their names. All outbound IPv6 TCP is denied, including mapped IPv4 addresses; API traffic must use IPv4. IPv4 loopback connections are restricted to the session's relay, the configured and validated proxy endpoints, and, for W5, the isolated bait service; ports 18765/18766 and any proxy collision with known service/relay ports remain blocked. For an approved CLI Batch, login bytes are read once by the CLI and injected into the private HOME, then deleted with it and redacted from evidence.

History seeds replay each recorded step under a separate historical author credential; these writes remain inside the seed boundary, including when a write commits but its reply is lost.

Before anything runs, the runner refuses what it cannot do (lifecycle/upgrade Controller actions: B02c) and an existing output directory. It supports sequential sessions, concurrent groups (`concurrent: true` starts with the previous turn), and `freshProcess` (a new isolated HOME and native thread, retaining the logical session label and credential). Two overlapping turns cannot share one logical session. Scripted replies still require the last assistant proposal in that session, including before a fresh process starts. A plan larger than `--ceiling` runs up to it and lists the rest as not run; Ctrl-C stops the client and service and marks what is left cancelled. Each Attempt writes `attempt.json` (the evidence record plus isolation facts: whether the sandbox was on, whether the service opened only its own database and never the everyday one, scratch/control/database cleanup results, isolation failures, built-in client skills, and whether every committed receipt matches a Revision its session's credential authored) and `raw/` (Codex JSON per turn, the session log for every turn, each relay's protocol observations, the service log and protocol report (initialization plus received tool-call metadata), the redacted final working directory), with credentials replaced by placeholders. `batch.json` lists every planned Attempt's outcome and compares personal configuration and the everyday service before and after.

`runner/runner.test.ts` covers the runner without a model: refusals, every library seed against the real service, the sandbox profile, and S0b played by `runner/fake-codex.mjs`, which makes real MCP calls.

`runner/sessions.test.ts` adds model-free runs on disposable services: two clients overlap and commit their own Revisions; a lost native receipt stays unknown even when relay logs and history prove a write occurred; a fresh process reads the existing Map and later resumes its new thread; S5/S10 gate their replies; S6 injects a real Conflict and stops if the read/write trigger or native Conflict receipt is absent; W5 cuts business calls and never credits Controller actions as agent work. Fixed evidence also covers wrong authors, mismatched Maps, missing history and duplicate receipts.

Each session has a separate relay. For a `conflicting-write` during a turn, the relay observes a successful `map_read`, then waits at that session's next `map_apply` boundary while the Controller commits its synthetic Fog. It forwards the agent's original RPC body unchanged and supplies that session's credential; the actual Conflict must appear in the native output before the scripted continuation is sent. A session that never reaches that boundary is `precondition-not-met`. Controller tool calls (seed, injection and history reads) and action outcomes have `actor: controller`; agent receipts come only from native tool results, checked against one unique post-seed Revision by that session's credential. Missing or inconsistent results stay `unknown`. Event order follows observed streamed output, never a guessed Revision interval.

W5 version 4 keeps initialization and tool discovery reachable while the relay returns HTTP 503 for `tools/call`, without forwarding those calls, using the neutral body `Service Unavailable`. Its required event needs both a native transport failure and a matching session/turn/tool relay-cut observation; structured service errors do not count. This lets a resumed `codex exec` process reach its model with the server's real metadata and observe a failed tool call; `mcp_servers.wayfinder.required` stays enabled. The fault applies to the entire HTTP envelope: a JSON-RPC batch containing any `tools/call` also drops its Resource and Prompt members. Every dropped member is recorded with `scope: whole-envelope`; Resource and Prompt calls in envelopes without `tools/call` still forward. The Attempt records this condition and counts observed initialization and discovery responses instead of asserting reachability. Its bait address and credential are generated only for the isolated service and redacted in raw files too, including localhost and schemeless address variants with a port boundary. Version 4 expands this detection; version 3 records keep their original verdict semantics. Lifecycle restarts and canary upgrades remain B02c; they are explicitly refused, never approximated.

The MCP-only driver re-exports the sandbox API from `runner/sandbox.ts`; B09b and the B02d Dedicated Entry use the same implementation:

```ts
const { controlDir, readOnlyDir } = prepareSandbox(scratch);
// Prepare intentional skill, shim and copied-login content under readOnlyDir.
const client = prepareClient(controlDir, bin);
const profile = writeProfile(controlDir, session, workdir, client, {
  readOnlyRoots: [skillRoot, instructionsRoot],
  mutableReadOnlyFiles: [copiedSourceLogin],
  denyWriteRoots: [immutableStateRoot],
  denyWritePaths: [stateDirectoryEntry],
  localPorts: [sessionRelay.port], // plus the isolated bait port only when required
  protectedPorts: allKnownServiceAndRelayPorts, // include endpoints owned by other controller processes
  proxyEnv: selectedProxyEnvironment, // proxyEnvironment(client === 'claude' ? subscriptionHome : null, inheritedEnv)
});
// Pass only profile.proxyEnvironment alongside the client's explicit base environment.
```

The shared sandbox and reviewer use the same six-key selector and endpoint validator in `proxy.ts`. The runner and both interactive clients forward `profile.proxyEnvironment`; the future Dedicated Entry driver must adopt and verify this contract (it is not implemented here). Only selected HTTP(S) proxy IPv4 TCP ports supplement the relay (and intentional bait), while every other local TCP route, all IPv6 TCP/UDP and local IPv4 UDP remain denied; public IPv4 UDP keeps the prior policy. Malformed routing and proxy collisions with 18765/18766 or registered service/relay endpoints stop setup before launch; live proxy grants are also excluded from later harness allocations. Batch records contain only enabled status and variable names. See [implementation evidence, Codex findings and Batch routing instructions](../../docs/implementation/shared-sandbox-proxy.md).

`prepareSandbox` creates and registers fresh control and staging directories; existing directories cannot be nominated as controls. The workdir must be a real directory at canonical `scratch/work`; fixture preparation rejects an existing symlink before copying anything. `writeProfile` checks both workdir and native HOME again with `lstat`, rejecting symlinks; the HOME must belong to that scratch and be disjoint from work/staging. All additional read roots/files are canonicalized and must lie inside that session's HOME, its workdir, this layout's `readOnlyDir`, or the exact installed Node/Codex directories. There is no sibling-HOME name scan and no exception for an arbitrary descendant of a personal or temporary directory. Any registered control directory is excluded. The staging root itself cannot be a read grant; select only intended child directories or individual mutable files. A root outside these prefixes is refused before the client launches, including roots in other Attempts and private cache/temp trees.

Node is granted its real executable directory, without its parent. Installed Codex is resolved from the runner's PATH; an npm launcher uses its verified `@openai/codex` package root and resolved platform package, without granting `node_modules` or the install prefix. Those installation roots go through the same validation and cannot overlap an Attempt. `prepareClient` copies a custom standalone driver into this Attempt's `client/` staging child, never its original parent; this also applies to a driver placed directly at the staging root. A program already in a staging child keeps that child as its immutable asset root. Additional assets must be intentionally prepared there. Keep a staged program and its assets in their own child directory (`prepareClient` uses `client/`), with mutable login copies outside that immutable tree. Placing a program in the scratch or its parent cannot make that containing directory readable. The fixed OS grants cover executable/library roots and named TLS/DNS/device files; the root directory `/` is granted literally for macOS startup, not as a subtree.

Read-only trees are visible to the client and must contain only intended instructions, skills or executable assets. Symlinks and multiply linked immutable files are refused. The profile, explicit immutable trees and staged driver are content-hashed. B02b and B02d keep the hashes in runner memory; B09b serializes them into the protected `launch.json` manifest, whose digest is pinned in the operator command. `denyWriteRoots` and literal `denyWritePaths` resolve existing symlinks component by component, including dangling links, before appending missing components. Unlike read grants, a denial may name a file or directory that trusted setup has not created yet. The canonical target and all parent entries remain write-denied; existing entries are identity-pinned. Trusted creation is accepted without dropping the denial or granting reads. Symlink loops and non-directory ancestors fail closed. Keep private runner evidence and controls outside every client-readable prefix.

`mutableReadOnlyFiles` grants literal reads of regular files with `st_nlink == 1`; it does not grant their directory or siblings. The same prefix/control exclusions apply, and mutable files must be disjoint from immutable trees. A trusted launcher may refresh content in place, while device/inode, mode, link count, type and canonical parent identities stay fixed. Only content hashing is omitted. B09b uses this option for its staged Codex login and B02d uses it for its per-run copied client login, never Controller or Wayfinder session tokens.

Profiles are per native HOME and reused on resume. Checks run before every launch **and after every turn**, including the last. A refused launch has no invented delivered prompt, agent process event or session turn; a failure after a launched turn marks the Attempt incomplete. B02b preserves its native evidence; Dedicated keeps safely readable launcher facts and a process result, but withholds the failed turn, client artifacts and Map export when integrity prevents safe collection/redaction. It explicitly names the missing turn, native files, work/outputs and Maps; if the runner capture cannot be read through its pinned parents, its launch entry is also marked missing. Attempt records store checked paths and outcomes; B02d retains its shared profile manifest under raw controls, and B09b launch controls retain the hashes separately. Metadata access is intentionally global: `ls -ld` can observe a control directory's existence/attributes, but listing children, reading contents and writing remain denied. `kern.proc*` sysctl reads are denied, and process-information access is denied by default with explicit exceptions for self and same-sandbox processes. `proc_pidinfo` can inspect the client's own child, while outside processes and separate sandbox instances (even loading the same profile) remain denied. Global PID enumeration, including `proc_listchildpids`, remains blocked; allowing same-sandbox information does not make that global operation safe. Sandboxed `ps eww` and `ps -E` return no environment bytes for another process in both attached and detached launches. Mach task-name ports are denied by default, with exceptions for self and processes in the same sandbox; native probes cannot read another process's CPU, event or VM statistics. Limited POSIX metadata (`getpgid`, `getsid`, `getpriority`) intentionally remains available, so process existence is not concealed. Those calls provide no environment variables, credentials or file contents; the separate read and inspection restrictions still apply. Signals to unrelated processes, including existence probes with signal 0, are denied; clients can still signal their own children. Process groups are killed on exit/cancellation, including SIGHUP.

In MCP-only, session and Controller tokens never enter child environments or command lines. Each relay replaces Authorization with its own session credential, and clients cannot reach another session's relay. The MCP-only Controller token stays in runner memory; all run credentials reach the service only as hashes in the private Caches file. Dedicated also gives the trusted launcher a private primary-token file for its service probe, and the real launcher passes its own registered session token to Codex; the shim explicitly rejects the Controller hash even if it is a registered owner, so degraded per-launch authentication cannot pass the primary/Controller token to Codex. The disposable bootstrap creates an unused primary credential inside the service process and uses the checkout's built service API.

`prepareSession` receives `loginSource: { contents: string } | null`; it writes supplied bytes and contains no login-path lookup or file-copy operation. Only the approved-Batch CLI reads the daily login. Tests construct synthetic bytes/configuration in `runner/test-state.ts`; there is **no general fs interception or protection claim**. Import order does not change login injection, as `runner/login.test.ts` imports the runner first and demonstrates injection plus denied access to a synthetic source HOME. Batch snapshots still use an explicit `personalConfigRoot`, synthetic in tests and the actual personal root for approved Batches. They include launcher-written `credential-owners.json`, `wayfinder-token` and Dedicated `AGENTS.md`, alongside the existing configuration/login paths.

Model-free tests attempt cross-Attempt and private-tree read grants, implicit program/Node parent grants, hard-link and control-file imports, attached/detached process-environment theft, Mach task-name inspection and signal attacks, workdir/HOME symlink replacement, staging-root grants, nested-parent replacement, final-turn tampering, cross-route access and rollout symlinks. Native regressions check `xcode-select -p` before compiling with Apple Clang, skipping absent developer tools without invoking the clang/xcrun installation shim. `runner/task-name-probe.c` checks four Mach task-info flavors and `proc_pidinfo` against outside and peer processes, self and a child, reporting only return codes and counts. `runner/tty-probe.c` uses `forkpty` to verify controlling-terminal read/write access, window size, terminal attributes, raw mode and denial of a second synthetic pty. `runner/terminal.test.ts` checks TIOCSTI injection through the actual interactive launcher into a disposable outer shell, six descriptor-alias shell idioms, and `openpty`/`script` with outside and peer-sandbox ptys still denied. Owned listeners verify that mapped IPv4, IPv6 loopback and wildcard addresses fail while the IPv4 relay works; the network denial rules are shared with the reviewer sandbox. A manual sandboxed `codex --version` launch also verifies the installed client's startup without a model; full real-session behaviour remains for the approved Batch.

For ChatGPT, use the separate [isolated Batch command and operating checklist](chatgpt/README.md). `plan` prints approval impacts and messages without starting anything; `run` requires the approval reference and owns a fresh database, service, relay and exclusive tunnel. The initial five and upgrade checks still need a real approved run; App, web and mobile remain separate. `chatgpt/chatgpt.test.ts` runs the fake-tunnel, no-model regression checks in `npm test`; the real Batch command remains manual.

## Codex Dedicated Entry

Select `--entry dedicated` to drive the repository's `scripts/wayfinder-agent/wayfinder` through its documented noninteractive passthrough. The default stays `--entry mcp-only`. Both Entries use the same Scenario inputs, Controller, native-output normalizer, receipts and allowlist sandbox. Dedicated Batches refuse `--no-sandbox`. Dedicated support remains **unverified** in `clients.ts` until its five onboarding checks have evidence from a Batch Kun approved; synthetic tests do not onboard it.

| Context | MCP-only | Dedicated |
| --- | --- | --- |
| Client invocation | `codex exec`, `--ignore-user-config` | Actual `wayfinder --harness codex --method mcp -- …`, including `--no-daemon` |
| Launcher instructions | None | Launcher installs its unchanged instruction template as the private `CODEX_HOME/AGENTS.md`, substituting the run's output path |
| Wayfinder Skill | None | Launcher installs the repository's MCP Skill, copied unchanged into the run's projected checkout |
| Configuration | Runner's command-line MCP configuration | Launcher's real `config.toml` template and command-line model, effort and MCP URL overrides |
| MCP unavailable | `required=true` makes client initialization fail | Launcher config does not require MCP; if it becomes unavailable after launcher probing, Codex may continue without the tools |
| Personal context | Denied by the allowlist | Also denied; the launcher's reference to project control planes does not make personal files readable |

The Controller creates and owns the service before invoking the launcher. All launcher overrides are supplied: `WAYFINDER_AGENT_STATE_ROOT`, `WAYFINDER_AGENT_SERVICE_DIR`, `WAYFINDER_AGENT_OUTPUTS`, `WAYFINDER_AGENT_PORT`, `WAYFINDER_AGENT_DATABASE` and `WAYFINDER_AGENT_CHECKOUT`; `WAYFINDER_AGENT_USAGE=test` marks launcher metadata as test use. `HOME` points to a runner-owned staging child under this Attempt's `readOnlyDir`, separate from the writable client home. Its copied login is pinned by file type, device/inode and parent identities; native auth may only link to that source or be a regular refresh file. Every turn rechecks those identities before synchronization and recollects refreshed login strings before writing evidence. No daily installation ID is imported. No new launcher overrides are needed.

The database and credentials live in a new directory under `~/Library/Caches/wayfinder-behaviour-tests/`; the writable client state and fixture workdir live in the Attempt's scratch, with outputs under `work/outputs`. `prepareSandbox` owns the policy directory outside scratch and the staging directory inside it. `readOnlyRoots` protects separate staging children for the unchanged real launcher/templates, the shim and the projected checkout; `mutableReadOnlyFiles` protects the copied source login. `denyWriteRoots` and `denyWritePaths` protect launcher state and parent entries, including `AGENTS.md` and `config.toml` before the launcher creates them. `writeProfile` and `verifyProfile` own policy generation, canonicalization, hard-link rejection, identity pinning and pre/post-turn hashes; Dedicated does not append policy text or keep another tree-manifest verifier. Its extra checks validate the launcher's actual installed text and native auth link/refresh semantics. Generic file identity, regular-file/single-link checks and hashing all use the shared sandbox helpers; there is one `IsolationError` type. Only the output directories need explicit Dedicated entry denials beyond the shared ancestor protection.

The projected checkout contains the unchanged MCP Skill and no service build: a lost service makes the launcher refuse instead of spawning an untracked daemon. The staged launcher is byte-identical to this repository's real script; it and the private shim use an absolute Python interpreter with isolated imports. The shim validates HOME, CODEX_HOME and MCP URL, records the launch credential for redaction, strips bootstrap variables, and enters the shared allowlist. The launcher's pruning keeps the runner-owned Controller/history credentials alive through resume. The client cannot read service storage, the repository checkout or verdicts. The only local TCP grant is its isolated service port; IPv6 and other local ports, including 18765/18766, stay denied. Local proxies remain fail-closed; a restricted channel belongs to #101.

The Controller stops only its own service and removes the database, credentials, scratch and shared control directory. Dedicated does not copy SQLite files or journals into evidence or retain them after a catalog failure; byte replacement cannot safely sanitize SQLite. History is available only through the redacted `maps` export, with `raw.database` explicitly listed as missing. `raw/` retains the effective policy, shim and shared profile manifest.

Each Attempt records `entry=dedicated`, the launcher surface, the additional context in `given[].extraContext`, and `raw/entry-context.json`: source names (including Skill activation metadata), installed text, hashes, whether that text appears in the native rollout, and redacted launch arguments and overrides. Installation is checked through the actual launcher-created Skill link; a staged copy does not count. Failed launches retain the context record with absent/unknown installation and missing-field markers. Installed context does not by itself prove the model read it, and the fake client never pastes these texts into its rollout. Raw outputs are saved under `raw/outputs/`. Both Entries use `runner/artifacts.ts`: shared redaction applies to every destination basename and file body (including binary data and bait-address aliases). Colliding redacted names get a deterministic `.redacted-N` suffix; directories are not merged and files are never overwritten. Symlinks and `node_modules` are omitted; regular-file checks use the sandbox helper. The launcher's Client ID remains its real `Codex:<model>:<effort>` identity; single-session write receipts establish attribution. Unsupported multiple-session and Controller-action Scenarios are refused before launch.

The report keys and compares cells by Entry, labels anomalous cells with their Entry and renders separate Entry tables. A Batch/Attempt Entry mismatch is refused, including when other records in that Batch are missing.

## Verdicts and the report

`verdict.ts` judges one Attempt against its Scenario: a confirmed must-not (common checks included) fails it even if the run was cut short or evidence is missing; otherwise an unfinished run is `incomplete`, a required event that did not happen means the Scenario was not exercised (`incomplete`), and any item a script could not decide stays open (`insufficient-evidence`) until two independent reviews agree, an arbitration settles their disagreement, or Kun decides; an item left open for missing evidence only Kun can decide, and a record made under an older Scenario version is never re-judged by the current one. Only when every must-not and expectation group is decided does an Attempt `pass`. A cell (Scenario × Entry × Combination × release) keeps every Attempt: pass and fail together are `flaky`, a failure is never hidden by another Attempt, an undecided Attempt blocks a pass, fewer decided Attempts than the run matrix requires (two for Codex · `gpt-6-astra`, one otherwise) is `incomplete`, another Combination is due one more Attempt after an anomaly or a result unlike the main Combination's, a new Combination or model needs a two-Attempt baseline, and real-problem Scenarios report whether the failure was reproduced on their original Combination.

```sh
node tests/behaviour/cli.ts check <attempt.json>…                       # one Attempt, item by item
node tests/behaviour/report.ts <batch dir>… --json now.json --md now.md  # all cells of the given Batches
node tests/behaviour/report.ts <batch dir>… --baseline before.json      # compared with an earlier report
```

The report lists new regressions, flaky cells, uncovered or undecided cells and failing cells first, each Attempt with the items that decided it, their evidence locations and its raw directory, then every cell. A cell is compared with the baseline only for the same Scenario version, visible model and numbering series; otherwise it says why it is not directly comparable, and the old results stay in their own report. Upgrade checks carry script items too and are judged the same way (`asScenario` in `upgrade-checks.ts`): the expected recovery follows the Resource support recorded for the client, reading the rules and rereading the Map before writing again when it can, stopping and asking for a refresh when it cannot; an outage or a missing result is never read as the client's choice.

## Reviewing recorded Attempts

```sh
# Plan only: no client or generation. Keep evidence and report outputs in the private run directory.
runs="$HOME/Library/Application Support/Wayfinder/behaviour-runs"
node tests/behaviour/review-run.ts "$runs/B/S12-1" "$runs/B/S12-2"

# Optional zero-generation preflight: native subscription authentication inside the same isolation boundary.
node tests/behaviour/review-run.ts --check-login

# Only after Kun approves this review Batch and its generation ceiling:
node tests/behaviour/review-run.ts "$runs/B/S12-1" "$runs/B/S12-2" --execute --batch REVIEW-B1 --call-ceiling 10
node tests/behaviour/report.ts "$runs/B" --json "$runs/reviewed.json" --md "$runs/reviewed.md"
```

For each Attempt with reviewable items, budget **4–5 CLI generations**: two small availability probes (one per exact model), two independent reviews carrying all the Attempt's evidence, and at most one arbitration covering disputed items. N Attempts need a ceiling of **5N**; no reviewable items cost zero. Probes spend quota; `--check-login` does not. There are no automatic generation retries or model fallbacks. Exit 1 means pending review/human input or failed authentication; exit 2 means usage/execution error. A decided behavioural failure is a completed review, not a command failure.

An ordinary command refuses unchanged evidence that already has a review round. A separately approved `--retry` can reread only unfinished items that need valid readings or arbitration. It never rereads a completed decision or an item left for the human by undecided arbitration. Every prior claim remains in the aggregate verdict, including a rejected output that claimed a violation. Two valid readings are required before arbitration; rejected outputs are preserved with their original status and a rejection reason, but do not count. A later agreeing pair cannot erase an earlier violation claim, and arbitration must address all claims across rounds. Confirmed violations remain failures. Only a human decision can clear the human boundary.

Claude under test uses `gpt-6.1-sol` twice and `gpt-6-astra` for arbitration; all other clients use `claude-sonnet-5-5` twice and `claude-opus-5-5` for arbitration. Claude model names in another harness also select the OpenAI reviewers. Review 2 sees the same complete evidence as review 1, without any earlier answer; arbitration receives the full evidence and all prior readings for each disputed item. The Driver never replays completions. Native IDs, including probes and rejected outputs, are persisted across rounds (even when evidence changes); neither explicit replay markers nor a repeated native ID count as another reading. Provider token-prefix caching is not a completion replay.

The input includes the Scenario's target, item criteria, required-event script results, every normalized session/turn/event, Map history, receipts, missing markers and rule surfaces actually recorded. It does not read raw paths named by the Attempt. Each decided item needs a reason, existing locators, and `support` entries with exact quotations and item-specific explanations. The final reply is valid quoted content for deciding what the agent said, for both `holds` and `violated`; it must also have independently quoted, relevant corroboration for the same recorded session and turn. That can be a concrete non-final agent event, a receipt matched to a recorded call/result, or a Revision matched to such a receipt. Every supplied support is validated, so quoting the reply while merely listing a receipt does not suffice. A user question or turn input is citable context, but cannot supply the independent corroboration. Dangling receipts, unsupported quotations and evidence from another turn are rejected. The validator checks provenance, quotations and turn association; semantic relevance and the conclusion remain the responsibility of both reviewers and the arbiter.

For any turn with no Map writes, including turns that call `map_read`, the packet provides `turnWrites[i][j]`, a deterministic projection of the original record for `sessions[i].turns[j]`. It covers **every Map in the complete catalog and every receipt**, including agent-created Maps and an empty catalog. A usable record lists no committed receipts in that session/turn and equal before/after heads for every Map. Heads are reconstructed from the seed and Revisions placed by receipts at Scenario-wide turn indices; a Map created in a later turn has `null` on both sides of the earlier boundary, while an earlier creation can have equal non-null heads in a later quiet turn. A creation or update in the reply's turn makes that no-write record unavailable, even if a different seed Map stayed unchanged.

The projection requires complete catalog/history/receipt/session records, known receipt outcomes, write-call/receipt matches, and a consistent Revision chain with every agent write placed by a receipt and its author Client ID. Gaps, orphaned or duplicate commits, unplaced Revisions and post-seed Controller changes with unknown turn boundaries withhold the proof. Multiple sessions additionally need recorded non-overlapping turn boundaries in Scenario order; timestamps never assign a write to a session or replace a receipt. These checks apply to both `holds` and `violated`. Other missing required fields still block `holds` as before.

Only usable no-write locations appear in `evidenceLocations`; null `turnWrites` entries cannot be cited. Quote the **entire generated statement**, including session/turn, empty committed receipts and all before/after heads, and explain its relevance to the item. A decorative fragment such as `{` does not qualify. The input artifact saves this projection with the complete underlying Attempt, and the verdict independently recomputes it. The old whole-single-Map `maps[i].history` shortcut is no longer a no-write source; individual receipt-backed Revision citations remain available. This supports S12/S0 with empty catalogs, S0b's proposal before a later-turn creation, and F11 only when no Map was changed in the reply's turn. A reply alone or paired only with the human's question remains insufficient for either conclusion.

The review and arbitration prompts include `citationGuide`, grouping this Attempt's exact event, receipt, individual Revision and context locators, plus each available no-write locator with its session, turn and copyable complete quotation. Locators use array positions, not event sequence or Revision numbers, and omit the packet's `attempt.` prefix. Message quotations use decoded text; turn quotations use decoded `input`, not its JSON. `contextOnly` includes both turns and human/user-message events; none supplies independent support. Structured event/receipt/Revision quotations must be substrings of compact `JSON.stringify(record)`, so `"tool":"map_read"` and `"tool": "map_read"` are different quotations. Every support is validated: an invalid extra quotation rejects the reading even when a valid no-write support is also present. The prompt requires a separate quoted no-write support whenever the conclusion depends on no Map change; a read call or a statement in `reason` is insufficient. `syntheticCitationExamples` demonstrates both `holds` and `violated` on a neutral color-label criterion in session `SYNTHETIC`, turn 37. Each has a final reply and independent no-write support; only its `output` object demonstrates the response format. Neither example concerns any Scenario or supplies evidence or a conclusion for the Attempt.

The output instructions require one JSON object with an `items` array and exactly one entry per requested ID, using `itemId` (not the input field name `id`), one concrete status value, a reason, evidence locators and support objects with `location`, `quote` and `explanation`. They ask for plain JSON with correct string escaping and no surrounding prose. Invalid syntax, wrong/missing fields and invalid support remain rejected and preserved verbatim; the parser, verdict rules and retry budget are unchanged. Clearer instructions and the example reduce avoidable format errors but do not establish a real-model pass without a separately approved run.

Missing evidence is checked per item by `missingForReview` and included in its prompt:

- Every behavioural item, including script escalations, conservatively requires the full rule and action trace. Unknown missing markers block `holds`. Explicit missing instructions/tool definitions and unknown rule fields also block it; instructions are legitimately absent in `toolsOnly` mode. Unknown tool results, null command exit codes, unknown receipts and unassigned agent Revisions block `holds` even without a missing marker.
- `status-narration` requires recorded messages, user inputs and supplied rules (to identify unrequested rule quotations). Missing Map/receipt/action-result details do not affect that count. Unknown markers still block `holds`.
- Usage, client version/surface and reasoning-effort metadata do not establish any item's behaviour, so their absence does not block it. Missing model identity is not exempt.

Missing evidence cannot establish `holds`, including in arbitration, but does not erase an evidenced violation. Thus the missing `given[0].instructions` and `given[0].toolDescriptions` in the historical B2 S0b-1/F11-1 records cannot turn into passing model verdicts. Script-proven results remain authoritative, script items explicitly escalated to the model join the review, and human/paused items stay outside it. Quality observations cannot fail a Scenario alone.

Inputs, native outputs, invocation arguments (including system prompt and sandbox policy), rejected/validated readings, arbitration reasons and `review-plan.json` are private immutable files under `<attempt>/model-reviews/<round UUID>/`. The approval and complete plan are written **before the first probe**. The command atomically appends a summary to `attempt.json`, preserves Driver fields and takes an exclusive lock. A hard-killed command may leave a lock or an unattached round; inspect and reconcile its private evidence before another invocation. Unattached rounds block new calls so their native IDs cannot disappear on a retry. The evidence hash excludes only review summaries: edited evidence makes old readings inapplicable, without deleting them. `judgeAttempt`, `cli.ts check` and `report.ts` use the same cross-round decision rule. Reportable model reasons redact local paths; full diagnostics remain in the private artifacts.

### CLI isolation and availability

The macOS Driver uses locally signed-in subscription CLIs. The controller never opens/copies credential stores or accepts API keys. Children receive only PATH, HOME, TMPDIR, LANG, USER/LOGNAME and six proxy variables: `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` and their lowercase equivalents. All reviewers and shared-sandbox clients use `proxy.ts`: Codex selects terminal values only; Claude merges settings env with terminal precedence, including explicit empty values. Codex never reads Claude settings. Only those six keys are selected; no API keys, tokens, `ALL_PROXY`, NODE_OPTIONS, hooks or other settings are forwarded. Missing settings are allowed; malformed/unreadable settings, non-string proxy values and invalid or non-HTTP(S) proxy URLs return fixed unavailable diagnostics without file contents, paths or URL values. Tests supply synthetic subscription homes and routing values. Local `auth status` / `login status` checks subscription authentication without a generation. Approved availability probes then check access to the two exact configured models; failure stops the Attempt without substitution.

Both CLIs run under the same outer `sandbox-exec` policy in a fresh empty working directory. The policy hides personal home, the repository, unrelated temporary files, resolved workspace symlinks and known managed-configuration locations; cached preferences through cfprefsd are blocked too. It denies workspace/file writes outside the disposable runtime and native authentication refresh exception. Only the runtime, CLI/Node installations and the native authentication resources below are opened inside the blocked file paths; the child cannot read the daily settings file. No daily settings are changed; scratch is removed after each invocation.

The network policy denies Seatbelt's `localhost` destinations and **all outbound IPv6 TCP/UDP** (local IPv4 UDP stays denied by the localhost rule), then adds only the configured HTTP(S) proxies' IPv4 TCP endpoints (up to four). The `tcp6 "*:*"` deny closes the `::ffff:0.0.0.0` route that Seatbelt's `localhost` matcher misses; it also blocks `::ffff:127.0.0.1` and `::1`, including on the proxy's port. The narrow `tcp4` allows follow the deny rules so the IPv4 proxy remains reachable. Proxy URLs on ports 18765/18766 are rejected as unavailable before any client starts. After URL parsing, only `127.0.0.1` and `localhost` proxy hosts are accepted; forwarded URLs normalize `localhost` to `127.0.0.1`. Each gets only its parsed port (default 80/443), using Seatbelt's `tcp4 "localhost:port"` spelling. IPv6, IPv4-mapped IPv6, other loopback and remote **proxy URL hosts** are rejected. Bypass lists create no exceptions, and absent/empty proxies add none: the IPv6 TCP deny still applies, so direct API traffic must use IPv4. An approved Batch must confirm native-client IPv4 fallback; tests do not claim real API availability.

On macOS's default lo0 configuration, direct TCP to other ports via `127.0.0.1`/`0.0.0.0` remains denied, as does local UDP; all IPv6 TCP is denied regardless of destination. Seatbelt's `localhost` matcher does not cover every IPv4 address in 127/8: this profile does not claim isolation of additional IPv4 lo0 aliases such as `127.0.0.2`. Tests do not add aliases or change host networking. The shared routing validator runs before client resolution and again when the shared sandbox grants endpoints; its normalized environment supplies the launched client. The runner and interactive host use the shared sandbox accepted in [PR #94](https://github.com/kun-g/wayfinder_map_service/pull/94), including the mapped-zero denial.

The proxy is a trusted part of this route. The socket policy cannot inspect HTTP `CONNECT` targets: a permitted proxy could relay to 127.0.0.1:18766 from outside the sandbox. Disabled tools/MCP and rejection of native tool activity remain necessary; the profile alone does not establish destination isolation through a proxy. `NO_PROXY`/`no_proxy` preserve the selected values, including empty overrides; forcing loopback bypass entries would affect compliant clients but would not prevent an explicit CONNECT to the proxy. Proxy URL userinfo is not printed by the controller, but a native client could echo it in verbatim stderr saved in the private review artifacts. Fixed controller diagnostics do not guarantee that native output omits such userinfo.
