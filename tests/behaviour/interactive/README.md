# Interactive acceptance (B09b, Issue #81)

This manual tool checks the four R9 capabilities separately in interactive **Codex CLI** and **Claude Code CLI**. It starts no model. The operator launches clients only after Kun approves the Batch. All committed records are synthetic; none establishes real client support.

`host.ts` reuses the runner's service, Controller, credential-injecting relay and hardened macOS allowlist sandbox. `cli.ts` imports explicitly named native files into B01 AttemptRecords and uses `verdict.ts` for script checks and content review. The B01 Scenario format, scripted W1/W7 verdicts and global client capability values are unchanged. Interactive variants B09Async, B09Prepare, B09Adjust and B09Continue now use **verdict version 4**: mixed-row human input is retained, proved nudges survive unknown turn boundaries, and review deduplication ignores format controls. Earlier versions cannot be re-judged as version 4. These four outcomes do not replace the complete W1/W7 checks or B09c/B10 human acceptance.

## Confirm support before collecting acceptance evidence

1. Read the current [Codex CLI reference](https://developers.openai.com/codex/cli/reference/), [Codex app-server reference](https://developers.openai.com/codex/app-server/), [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference) and [Claude hooks reference](https://code.claude.com/docs/en/hooks), plus the installed binaries' `--help` and `--version`. Record the exact version, surface, mode, flags, model and effort. App-server support is not proof of CLI support; a blocking question tool or queued input is not asynchronous questioning.
2. Run one **separate approved minimal probe per Combination** with the same subscription authentication, Entry and isolation as acceptance. Ask it to propose a synthetic choice, ask for an answer without ending the turn, read a harmless fixture while waiting, adjust the recommendation to a contrary answer, and ask the next concrete question without a nudge. Wait for completed useful output, not a timer. Do not install a new tool or change mode to manufacture support.
3. Independently classify each capability as supported, unsupported or unverified. Supported requires the earlier probe's native JSONL **and Controller capture**, exact file hash, native line references, selection of relevant events, and an operator reading. Confirmation must finish before acceptance capture starts. Unsupported is an explicit operator declaration citing the version/mode documentation and reason; its coverage gap is not a passed probe. A missing observation remains unverified.
4. The importer actually parses the probe: it checks its time range, distinct native session ID, version, model, effort, surface, Entry, declared capture window and the native structural evidence for the claimed capability. `./` aliases, identical copies, same-session records and backdated metadata are rejected. Keep both redacted probe files and copy only those files into the fresh acceptance directory. If the acceptance record lacks model/effort/version evidence, the outcome stays insufficient evidence instead of borrowing the requested settings.

5. During the approved interactive probe, start a harmless tool process, cancel that turn, and verify that the tool and its children exit. Retain their known PIDs and exit observations from the outside observer; inspect or signal only processes created for the probe. `proc_listchildpids` remains denied to avoid exposing the global PID list, so successful cleanup must be observed rather than inferred from an empty child listing.

The adapters intentionally recognize a conservative native subset. The synthetic Claude `system/init` effort field is a parser test, **not a claim that the installed Claude emits it**. Validate the real format in the approved probe. Missing effort, unknown format, sidechains, compaction, ambiguous queued input or missing boundaries cannot establish a positive same-turn claim; never fill actual model/effort from requested flags. Already observed violations remain visible. Changes to native schemas require fixed regression evidence before wider acceptance.

## Subscription prerequisites

API-key billing is removed. The trusted outer launcher builds an explicit client environment without `CODEX_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, Wayfinder tokens or OAuth token values. It does not parse or print login contents or copy keychain entries. The approved host preserves a newer Codex refresh as described below; worker tests use synthetic files only.

- **Codex:** the host prepares an empty mode-0600 staging file, and the trusted outer launcher fills it from the current `~/.codex/auth.json` as opaque bytes immediately before starting the client, preserving source timestamps and the pinned destination inode. The private CODEX_HOME login links to that copy. The outer sandbox grants only the copied file as mutable read-only data, never the personal source path or its directory. Normal config, sessions and other private files remain denied. After the client exits, the host checks whether refresh replaced the symlink with a regular file. If that file is newer than the daily login, it backs up the daily file as `auth.json.bak-<timestamp>-<unique-id>` and atomically replaces it with the refreshed copy, both mode 0600, without parsing or printing contents. A replaced login directory or multiply linked refreshed file is refused before reading it. An unchanged symlink to the staged copy is never followed during cleanup; an older scratch file never replaces a newer daily login. If synchronization fails or the daily file changes during the copy, the host records `driver-failed` and retains scratch for the coordinator: stop further runs until recovery. After a launch, retained scratch contains a mode-0600 subscription copy under `read-only-*/login/auth.json`, and may also contain a refreshed login under `home/.codex/auth.json`. Never delete retained scratch before resolving that refresh; after recovery, delete the retained scratch and its login copies before another run. `--no-daemon` keeps the MCP connection inside the isolated process. The unsupported interactive `--ignore-user-config` flag is gone. Fresh HOME/CODEX_HOME provide configuration isolation; the external sandbox remains authoritative.
- **Claude Code — requires Kun's action:** this isolated host keeps a scratch HOME and therefore does not use the normal keychain route. Before the Batch, Kun must approve **`claude setup-token` in the browser** if no valid subscription OAuth token is available. Only Kun performs that step. Supply the resulting `CLAUDE_CODE_OAUTH_TOKEN` through the private operator-terminal environment without echoing it or saving it in repository files. The trusted outer launcher requires that variable and sends its bytes over inherited descriptor 3, with only `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR=3` in the client environment. It never writes the OAuth value into the manifest or client argv and has no API-key fallback. This descriptor entry point is present in the installed Claude binary; fake-client tests verify the handoff through Seatbelt, while actual subscription use still needs the approved probe. The host passes exactly `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `http_proxy`, `https_proxy`, and `no_proxy`: a value in its terminal environment takes precedence over the corresponding `env` entry in `~/.claude/settings.json`, matching the dedicated launcher. No other settings environment key is passed. Unreadable or malformed proxy settings stop setup instead of silently falling back to a direct connection. The selected proxy values do not broaden the sandbox: only the session relay has loopback access, so an additional local proxy fails closed and needs a separately isolated route before use. Confirm the intended proxy in the approved probe; do not paste proxy credentials into a report. Never copy keychain entries. The alternative documented in the dedicated launcher (`CLAUDE_SECURESTORAGE_CONFIG_DIR` empty with the real HOME) is deliberately not used here because it would broaden this host's isolation boundary.

The subscription route must pass the minimal probe before acceptance. The worker does not run login, auth-status, setup-token, credential reads or real model sessions.

The host does not copy daily installation IDs; a fresh Codex/Claude config can create a new installation identity. Include that fact in the probe approval request to Kun before running it; it is not assumed accepted. Keep other Codex clients and login/refresh operations stopped until this run's refresh synchronization or recovery finishes. The metadata recheck reduces concurrent-update risk but cannot make a cross-process compare-and-rename atomic. A failed sync may leave a private `auth.json.bak-*` backup as well as retained scratch; no automated recovery command is provided here, and recovery remains coordinator-owned before another run.

## Start a private Attempt

```sh
export PATH="$(dirname "$(npm exec --yes --package=node@26.3.0 -- node -p process.execPath)"):$PATH"
npm ci
npm run build

# Separately, after approval, using each actual absolute binary path.
node tests/behaviour/interactive/host.ts B09b-approved codex-W7-1 codex gpt-6-astra xhigh W7 /absolute/path/to/codex
node tests/behaviour/interactive/host.ts B09b-approved claude-W7-1 claude claude-sonnet-5-5 high W7 /absolute/path/to/claude
```

Use a fresh Attempt name for each probe and each W1/W7 repetition. The host refuses existing directories. It creates only its own database under `~/Library/Caches/wayfinder-behaviour-tests/<batch>-<attempt>/`, a free port excluding 18765/18766, distinct Controller/agent credentials, and scratch HOME/work directories under `/private/tmp`. It injects no Skill, AGENTS.md, workflow or service version into the client. It never starts a tunnel, `wayfinder`, or the everyday service.

Keep the host terminal open; run its printed Node command in another terminal. That command pins a SHA-256 digest of the launcher manifest in the runner-owned control directory outside the client-writable scratch. `launch.ts` first reserves an exclusive mode-0600 `launch.once` marker, then verifies the manifest and shared profile/immutable-file hashes before starting the client and checks profile integrity on exit. Each command can be attempted only once, even if authentication or integrity validation refuses its first attempt; arrange prerequisites before invoking it and create a fresh Attempt for any retry. A second invocation is recorded as refused without starting another client or altering the first launch's outcome. The client cannot read or write these controls. Its MCP configuration contains only the relay URL; the relay attaches the session credential in runner memory. Codex uses its subscription link; Claude requires the subscription OAuth variable in that terminal. Both use process-local MCP configuration, the outer `sandbox-exec` allowlist, and explicit approval modes suitable for that external sandbox. Verify those modes in the probe. The host has a 60-minute ceiling. Stop the manually launched client before finishing or cancelling the host; if timeout, cancellation or lost input prevents exit attestation, the host retains scratch and controls and defers login synchronization for coordinator recovery; the operator still attests exit because wrapper status cannot prove all client descendants have exited.

## Operator checklist

1. Complete all capability confirmations and subscription prerequisites first. Preserve the probe JSONL and its capture before starting this Attempt. Use the host's opening line for W1/W7; do not paste this checklist, acceptance criteria or copied workflow rules into the client.
2. Answer only a proposal actually shown. For W7, supply a concrete contrary constraint, such as mobile-only entry when the proposal assumed desktop access. Record the actual answer. Do not send a nudge to manufacture continuation. An absent required proposal ends as `precondition-not-met`.
3. Record completed preparation while the answer is pending. Select a real output finding and cite where the later recommendation uses it. Agent/Task launch notices, lifecycle calls, command exit status and `sleep` are not findings. A faster next turn is observation only.
4. Exit the client first, then give the host its actual outcome: complete, precondition-not-met, launch-failed, timeout, rate-limited, cancelled, driver-failed or service-failed. Every started host Attempt retains a capture, including setup/service failure. Missing records remain missing.
5. Inspect `isolation.json`. It contains configuration-equality and run-path checks, listener/database metadata snapshots, the actual service exit result, its observed open database, Codex refresh synchronization status, and control-integrity checks. The host copies `launch.jsonl` into `raw/` before cleanup, retaining start/exit timestamps, exit code, signal and refusals. Nonzero or signalled exits remain evidence alongside the operator outcome; they do not by themselves turn `complete` into `driver-failed`. After a command is exposed, `complete`, `precondition-not-met`, `rate-limited`, `timeout` and `cancelled` all require a `started` record; without one they become `launch-failed`. More than one start becomes `driver-failed`. A `complete` declaration also requires exit evidence; missing exit evidence or integrity failure becomes `driver-failed`. A rejected duplicate invocation is retained in the log and does not count as another client start. Known launch/integrity failures cannot become complete through operator attestation; unknown system observations remain unknown. Configuration files may contain secrets: their hashes exist only in memory for comparison and are omitted from the report. The observer does not read auth files, service credentials or database contents; subscription refresh preservation is a separate cleanup step. A missing observation is unknown. Stable snapshots do **not** prove absence of transient calls to the everyday service; that claim remains explicitly unknown. No request is sent to the everyday service. Cleanup removes this host's scratch and controls only after successful refresh handling and removes its temporary Wayfinder credential file; private test database/evidence and any login backup remain.
6. Select the main session by native ID from `raw/native-*.jsonl`; never combine sessions or parent/child logs. Copy the fixture assessment as a **shape only**, replace every synthetic value, and keep `reviews: []`. The fixtures contain no ready-made reviews. Set `verdictVersion: 4`, event selectors, `preparationFinding` (an exact quote from completed output) and `preparationUse` (an exact quote from the later recommendation). Unknown facts stay unknown.
7. Import once without reviews. Use the emitted `review-input.json`, which contains the complete captured Attempt plus the four criteria and selections, for two independent other-vendor review sessions. Retain each actual input, output, visible model, reviewer and native session ID; the same cached output is not an independent reading. Review output may be one bundle with `items`, each naming `ability`, `status`, `reason` and `evidence` (native event `seq`, exact content `quote`, and an item-specific `explanation`). There is deliberately no pre-filled `holds` example.
8. Supply a **separate** `wayfinder-interactive-reviews/1` manifest through the CLI's optional fifth argument. Each `records` entry identifies ability, role (`review` or `arbitration`), reviewer, sessionId, vendor, model, and input/output references (`path`, `sha256`). A grouped output file may be referenced for its four items. All primary selected events must be cited; additional quoted events may supply the shared B03 same-turn corroboration requirement. Arbitration also retains `basis` references to both independent outputs. The importer verifies hashes, exact Attempt/input binding, cited event content, distinct reviewers/sessions/outputs and the R4 vendor/model route. Punctuation, case and whitespace changes do not make a second independent reading. Labels and hashes cannot authenticate a model invocation or detect every paraphrase: the coordinator must retain the two actual review runs and their native session IDs. A settled agreement is final; only disagreement or an undecided reading may have an arbitration entry. Re-import into a fresh output directory; earlier results remain intact.
9. File-supplied human verdicts are rejected, including entries claiming `by: Kun`. Generic `capture.modelReviews` annotations are also rejected: they cannot bypass the separate interactive review path. The importer cannot authenticate a human and therefore leaves missing evidence open. When Kun is needed, the coordinator asks him through the authorized human channel with the Attempt ID, item, review-input hash and native event locations, then preserves his actual reply and those bindings in the separate acceptance record. No local file can turn that into a machine `pass`; B09c/B10 acceptance stays with Kun.

`lsof` is an opportunistic open-file observation. No matching SQLite file, a WAL-only listing, or an unavailable query leaves `servedOwnDatabase` unknown; none proves that the requested database was used. An observed different SQLite path is false. The host lifecycle tests accept documented missing observations while still rejecting an observed mismatch; a synthetic empty `lsof` executable exercises that route without relying on the test environment's permissions or timing.

## All-unsupported preflight

The ordinary host capture deliberately leaves `client.version` unknown until import. For the `-` route, the coordinator must first retain the exact `--version` output from the preflight (no model session), and record confirmations with that exact string, surface, documentation, reason and earlier `checkedAt`. Finish the service-only host as `complete` without invoking its printed client launcher. Keep that original capture intact; create a **separate** `preflight/` directory with `client-version.txt`, the all-unsupported `assessment.json` (`reviews: []`), and a derived `capture.json`. The following offline step only copies the observed version into that derived envelope:

```sh
node --input-type=module - "$HOME/Library/Caches/wayfinder-behaviour-tests/B09b-approved-preflight" <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
import { join } from 'node:path';
const root = process.argv[2]; // preflight/ and its version/assessment files already exist.
const capture = JSON.parse(readFileSync(join(root, 'capture.json'), 'utf8'));
const version = readFileSync(join(root, 'preflight/client-version.txt'), 'utf8').trim();
if (!version) throw new Error('Missing observed client version');
capture.client.version = { known: true, value: version };
capture.raw = { path: '.', files: ['client-version.txt'] };
writeFileSync(join(root, 'preflight/capture.json'), JSON.stringify(capture, null, 2), { mode: 0o600, flag: 'wx' });
JS
node tests/behaviour/interactive/cli.ts "$HOME/Library/Caches/wayfinder-behaviour-tests/B09b-approved-preflight/preflight" - assessment.json judged-1
```

This is explicitly an operator-declared preflight with retained version evidence, not a machine-verified support probe. It can produce not-applicable gaps, never pass. Unknown support stays unverified and cannot use this route.

## Evidence limits

Asynchronous asking requires question, completed work **and answer in the same active native turn**. Preparation requires actual completed output before the answer and evidence of its later use; semantic relevance still needs review. The allowlist accepts direct read tools, Map reads, and conservative read-only commands with a successful structured result and real output. It excludes `sed`, preprocessing commands and follow/in-place flags. Native string-form shell results remain unknown until an approved probe supplies a format and a regression fixture; arbitrary shell/agent-control success cannot count. Adjustment compares the original proposal, changed answer and new recommendation. W1 continuation requires answer and next concrete question/action in the same answer-handling turn, with no intervening nudge; its earlier question may belong to a previous turn.

Codex uses task_started/task_complete and response_items; duplicated event text is not double-counted. Claude uses transcript user/assistant blocks, tool IDs and explicit end_turn/turn_duration boundaries. Rejected/cancelled question results, including string `is_error: "true"`, are not human answers. Synthesized answers retain their question-tool origin: a blocking tool cannot prove asynchronous delivery even when the selected question is an earlier assistant sentence. A Claude interruption closes the active turn. An uncorrelated second user-text row or an ambiguous queue record makes delivery/turn identity unknown for subsequent events in that turn; a missing end marker never proves mid-turn delivery. A new turn after an explicit end can still prove W1 continuation. Recognized metadata and rejection text beside tool results are not human choices. Unknown model or effort blocks pass, and conflicting observations are not overwritten by a convenient later value. A proved temporal violation remains fail even when a run times out. Requested-versus-visible model/effort mismatches retain an insufficient-evidence result; aliases are not silently equated. Confirm the canonical observed ID and effort format in the approved probe.

The current Claude native adapter has no documented positive mid-turn delivery marker, so it cannot establish asynchronous delivery from plain transcript rows. Positive verdict tests use separately constructed complete B01 unit records for both clients; the Claude native fixture explicitly ends the first turn before the answer and leaves async support unverified. Adding a real native decoder requires the approved probe first, never an invented marker or a capability-table promotion. Preparation remains an independent completed-output/content check, with an observed work turn; it does not imply asynchronous delivery.

Claude user text beside a tool result is retained block by block; only a whole recognized rejection notice is excluded, not further words sharing its block or row. Uncorrelated delivery still makes the affected turn unknown. Ordered human input between the selected answer and continuation in one session proves a nudge without turn identity, so both clients fail continuation even with missing boundaries or other trace gaps. Corrupt event ordering cannot prove that violation. Question results with any error flag other than absent or explicitly false cannot create synthetic human answers. Review deduplication also ignores Unicode format controls such as zero-width spaces and soft hyphens.

The shared B03 review gate also requires native reading IDs, explained source quotations, independent corroboration for any cited final reply in the same turn, and the complete GivenRules/action trace for a positive reading. The interactive importer forwards that evidence and does not weaken the gate. Its current conservative native adapters leave rule exposure and several action classes uncollected; even two positive reviews of those incomplete native imports stay insufficient evidence. `result.json.reviewIssues` retains the rejected-reading reasons. Filling those native trace gaps is separate probe-driven adapter work, not a reason to clear `missing` or borrow Controller-only rules. The complete B01 unit fixtures are never used to enrich an imported native record.

All host and offline-import outputs use the scrubber, and known secrets keep the same placeholder in headers and other references. This is not proof of complete credential removal: the client can read its own subscription credentials, and an unfamiliar bare login value printed without a recognizable key/prefix may survive generic scrubbing. The worker never opens real login contents to build a secret list. Keep raw evidence private; the coordinator must check it before any export and must not treat `leaks()` (which checks known Wayfinder/proxy values) as an exhaustive login audit.

Only complete named placeholders survive generic Bearer/token-field scrubbing; a placeholder prefix cannot hide an unknown credential suffix. HTTP(S) proxy URLs remain private values for redaction, while `NO_PROXY` and `no_proxy` are routing lists, not credentials: their loopback host names stay readable in captured MCP URLs.

Rules seen only by the Controller are never claimed to be shown to the model. Missing usage, file/delegation classes or process evidence remain explicit. Native formats and subscription operation still need the approved real probes; synthetic fixtures prove only the testing tool. Validate without models:

```sh
npm run build
npm test
npm run typecheck
```
